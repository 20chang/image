## 二、此前建议的取舍

我逐条重新判了一遍，**有三条我之前的建议在当前仓库是错的**，先认下来：

| 我此前的建议                  | 现在的判断               | 理由                                                         |
| ----------------------------- | ------------------------ | ------------------------------------------------------------ |
| 参数化区间 + 理由的设计决策表 | **暂缓，且我收回优先级** | 零出图、零失败案例。现在建表就是空壳，而且**你无法观察一个决策错在哪**——没有对照物。 |
| 养成器 + 四桶归因             | **本轮明确放弃**         | 同上。没有失败案例可归因。这套东西的完整形态要到有 20+ 真实出图之后。 |
| 任务包                        | **取消这个名字**         | 仓库里没有这个概念。最近的对应物是 `case.json`，但它是测试夹具，不该背负任务包的语义。 |

保留下来的，按"现在/调整后"分：

**✅ 保留，且是本轮第一优先：模型适配层。**

之前我说这是"最脏最快过期的一层"，读完后我改判了：**这不是提前建设，这是候选方向能否成立的前提。** 因为 `model` 字段是 `"TBD-next-round"`，图片根本没进 messages。在这两件事修好之前，Skill 组装做得再干净也只是"格式正确"。

但**做法的口径要改**：不要建 provider 抽象层。**一个函数 + 一个模型名字符串 + 一个配置文件**就够了。等真的接第二个模型再抽象。现在建抽象层是在给一个不存在的多态性写接口。

**✅ 保留，但定义要改：案例快照。**

我原来的说法是"存 rules 引用"。读代码后我确认这样不够——**`skills/*.md` 是会变的 git 文件**。运行记录如果只存 `rules_version: "HEAD@1221e29"`，事后无法重建当时到底喂了什么。所以快照必须**内联规则正文和输入正文**，不是记指针。这条现在从"建议"变成了"有代码依据的必需"。

**⚙️ 调整：确定性 Prompt 编译。**

`assemble.py` **已经**是确定性组装了，这部分你有了。我说的是"确定性提取"——即把规则里的可判定约束变成代码。目前 `main.md` 里只有一条够格：**「缺少 primary 不得生成」**。我实测它不生效。

所以正确的做法不是"把六族知识都编译成结构化规则"（现在 5/6 族是空的，编译不了），而是**挑这一条最狠的做成代码检查**。这是"不改知识格式"和"不做全面结构化"之间的中间位置。

**⏸ 缺前提：按类目/材质/平台检索。**

现在只有"族"一个轴，而且只在 CLI 层。更关键的是：`products` 表**没有类目字段，没有材质字段**，只有自由文本的 `market`。这条要等这些字段存在才谈得上。我建议这轮**只在 spec 里写明这个依赖关系**，不建任何东西。

**⏸ 暂缓：回归评测。**

前提是真实出图 + 评分，两者都没有。但要在下一轮 spec 里记下 `now_iso()` 分钟精度这个雷。

当前状态：**知识是"整篇塞进 system prompt"，经验是"人工写进一个 .md 文件"。** 两端都没有接口。

## 三、下一轮可交给开发者的任务

### 目标（一句话）

**让"看图规划"这件事真实发生一次：图片进入模型请求，输出可落库可采纳，并留下可复现的运行记录。范围只限 `main` 族。**

我不建议按你候选方向的完整顺序做（Skill 组装 → 采用到草稿 → 运行记录 → **之后**接生图与评价）。理由：**"之后接评价"这个顺序是反的。** 如果不先收一批真实图，就永远不知道 `main.md` 的规则在真实出图下错在哪，Skill 组装做得再对也只是格式正确。

但也不建议本轮就接生图 API——那会引入计费、超时、重试、失败补偿一整套问题，而你现在需要的是**判断知识对错**，不是**批量出图**。

**建议的解法**：本轮跑通到"落库 + 可采纳"为止，**出图在系统外手动做**（可灵/即梦），人工评分先记在纸上或表格里。下一轮再决定要不要把图和分收进库。

- **为什么现在做**：已确认方案是不可变的（`update_image_plan` 409）。**你需要"同一个 prompt 改了规则之后再跑一次"来对比效果**，这个血缘指针是唯一的载体。不做这个，评估闭环断在这里
- **验收**：从已确认方案复制出新草稿，`basedOnPlanId` 正确指向来源，两者 `status` 分别为 `confirmed` / `draft`，复制后修改新草稿**不影响**原方案

---

**本轮明确不做**：养成器、四桶归因、回归集自动跑、另外五族、类目/材质/平台知识轴、生图 API 接入、知识格式全面结构化迁移。

## 四、完成后的后续两步

### 第一步：用真实图片判断知识有没有价值（不做自动化）

进入条件（本轮全部完成 + 验收通过）：`main` 族方案能真实调出规划模型，输出能落库能采纳。

**具体做法**：

1. **选 8–12 个商品，覆盖材质差异**。至少要有：金属（反光强）、塑料/哑光（吃光）、透明或半透明（边缘难处理）、深色（暗部糊）、多部件带线束（结构易幻觉）。**别只挑最好做的**——你现在只有一个车灯案例，它恰好是金属+浅色+结构清晰，是最不需要经验就能出活的一类。
2. **每个商品准备 2–3 张参考图**，按现有 `referenceUsage` 配好角色。
3. **出图在系统外手动做**。把 `prompt` 复制到可灵/即梦/SD，参数固定。
4. **人工评分，只记三个数**：
   - 商品是否准确（结构/部件数/颜色/logo 有没有跑偏）
   - 任务是否完成（主图该说清的说清了吗）
   - 返工几次才可用

**这一步的真正产出不是分数，是一份失败清单。** 每一张不合格的图，你要写下它错在哪——这才是后面归因的原料。

**一个纪律**：不要用"跑通了一次"当结论。你现在最需要的恰恰是**失败样本密度**。如果 10 张图里有 8 张能用，恭喜，但你的知识体系还什么也没学到；如果只有 3 张能用，你学到了 7 件事。**第二种情况对你更有价值。**

**进入第二步的条件**：至少有 6 条具体的、可复述的失败描述，且能对应到 `main.md` 或 `common/` 里的某条规则或某个缺失。达不到就继续攒，不要开始建养成器。

### 第二步：建设养成器（但只建四分之一）

进入条件：失败清单成型，且你已经能看出**失败是"知识错了"还是"模型没听话"**。

**先建的部分**：

1. **失败记录进案例**。给 `skills/cases/` 定一个 schema：`(商品属性, 族, 决策, 最终 prompt, 结果图, 评分, 失败类型, 证据)`。注意——**现在 `car-light-main.sample.md` 是"人工编写的理想输出"，不是"案例"**。它没有绑定任何一次运行，没有失败，没有分数。**它是设计意图文档，不是经验。** 真正的案例必须来自 `plan_runs`。
2. **只做四桶归因，不做自动化**。人工判定每个失败属于：知识错缺 / 未检索到 / 模型不听话 / 转译丢失。**记录判定结果，不写代码。**
3. **看一个指标**：`bucket 3+4` 占比应该随时间下降，`bucket 1` 先升后降。如果 `bucket 3` 一直高，说明瓶颈在 prompt 结构和转译，**加多少规则都没用**。

**明确不做的**：自动提案、自动改规则、自动回归、规则退役机制。这些等你已经有 20+ 案例、并且真的被重复劳动逼到过，才值得建。

**退役机制现在提一句**：等案例超过 30 条，记录每条规则的"被调用次数"和"被修正次数"。调用很多次但从不需要修正的、或者总被方案覆盖的，**都要准备删**。知识库只增不减的话，第二个年你就没人敢动它了。这一点几乎所有人都会踩。

## 收尾

**你现有资产比我预期的多，不要动它们。** 三个设计我认为是对的，值得明确保留：

1. **参考图身份与顺序分离**——`refImageId` 稳定、A/B/C 只是按数组位置派生的展示标签，文字说明和图片输入共用同一个 `ref_rows` 迭代。这套语义是干净的，**T2 直接复用它，不要重写**。
2. **`attrs_migrated` 哨兵**（`db.py:101`）——用标记位而不是列默认值来防止迁移覆盖用户写入。这个思路比代码本身更值钱。
3. **`main.md` 的"结构必须有依据"和 sample 里的「已删除的无依据细节」清单**（透明灯罩、黑色接头）——**这是负向知识，比正向规则更值钱，而且已经在你的仓库里了。** 养成器建成之后，每条失败都该能落成同样形式的"已删除的无依据细节"。

**六族不用重构，知识格式不用迁移。** 5/6 族是空壳不是问题——那是"还没写"，不是"写错了"。等有了失败清单再填，填的时候你会知道该填什么。现在迁移 Markdown 到结构化格式，是把一个还没成形的东西提前定型。

**至于你候选方向里的顺序**，我唯一的实质反对是「之后再接实际生图与评价」这个排期。**评价要提到出图前面，哪怕先手工。** 其余（family 落库 → 图片进请求 → 输出落库可采纳 → 运行记录）我完全同意，就是上面 T1–T6 的顺序。
